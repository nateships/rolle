## Long-lived secrets

Identity Center refresh tokens, console login refresh tokens with their DPoP keys, Azure token caches, and IAM user access keys live in the OS keychain (macOS Keychain, Windows Credential Manager, Secret Service on Linux) under the service name `rolle`. Large tokens are split into chunks.

## Short-lived credentials

A started session caches its temporary credentials in the OS keychain, one entry per session, next to the long-lived secrets. `credential_process` reads that entry. Each entry carries its expiry. The app renews or removes entries, and a stale entry is removed on the next read. No credential is written to disk. An IAM user without MFA has no temporary credentials. Its access key stays in the keychain and does not enter the cache.

**Open terminal** writes a short launcher script under `credentials/launch/` in the cache directory (see [Storage](/#storage)). The script deletes itself as its first action and asks `rolle env` for the environment when the shell starts, so it never holds a credential.

## AWS profiles

rolle marks each profile it writes with a `rolle_session` key. It does not touch a section that holds `aws_access_key_id` or other credential keys. It takes over a plain `[default]` section that sets only region or output, and restores it on stop.

## No telemetry

rolle sends no analytics, no crash reports, and no usage data. It has no account. It connects only to:

- The cloud providers you sign in to: Identity Center portals, AWS OIDC and STS, Microsoft Entra and Azure Resource Manager, Google APIs, and the consoles that **Open console** opens in your browser.
- `github.com`: the update manifest at launch and every six hours while **Settings → General → Automatic updates** is on, the update download you confirm, and the issue form that **Report a problem** opens in your browser.

The support bundle is a file in your Downloads folder. You choose whether to attach it to an issue.

Four checks:

- **Host log.** Run `rolle --debug` or set `ROLLE_DEBUG=1`. Every HTTP client in the process, cloud SDKs included, uses one transport. It logs the method and the host of each request, nothing else. **Verbose logging** in the desktop app does the same. The support bundle carries the last lines.
- **Capability analysis.** [Capslock](https://github.com/google/capslock) reads the Go call graph and reports the capabilities each package reaches through its dependency tree: network, process execution, file access. `capslock.json` in the repository holds that set. The `capabilities` CI job fails a pull request that changes it.
- **[OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/nateships/rolle).** A weekly independent rating of the repository: pinned actions, branch protection, signed releases, token permissions, static analysis, dependency updates.
- **Provenance and reproducible builds**, below.

## Enterprise networks

rolle verifies TLS against the OS trust store: the macOS Keychain, the Windows certificate store, or the Linux system bundle. A corporate root installed there needs no rolle configuration. For a root in a file, point **Settings → Advanced → Extra CA bundle** at the PEM. **HTTPS proxy** routes every request through one proxy when the app does not see your shell's `HTTPS_PROXY`. Both apply to the CLI and the app, AWS SDK calls included.

## Signed updates

An Ed25519 key signs every release manifest. The desktop app verifies the signature before it installs an update. A Developer ID certificate signs the macOS builds, and Apple notarizes them. A Certum code signing certificate signs the Windows installer, app, and command with an Authenticode signature and an RFC 3161 timestamp; the key stays in Certum's cloud HSM, and the release workflow signs through [ssign](https://github.com/Le-Syl21/ssign). `checksums.txt` lists every release asset and carries a keyless Sigstore signature from the release workflow. [Install](/install#verify-a-download) shows the check.

## Build provenance

The release workflow writes a [SLSA build provenance](https://slsa.dev/provenance) attestation for every file in `checksums.txt`. It names the repository, the commit, and the workflow run that built the file. GitHub signs it with the workflow's identity. Check a download with the GitHub CLI:

```sh
gh attestation verify rolle.dmg --repo nateships/rolle
```

A pass means `.github/workflows/release.yml` in this repository built the file at the named commit.

## Reproducible builds

The `rolle` command inside every desktop package is built with `-trimpath -buildvcs=false` and without cgo. The same source, toolchain, and flags give a byte-identical binary. To check a release: install the app, clone the tag, use the Go version that `go version -m rolle` prints for the installed command, and build.

```sh
git clone --branch v<version> https://github.com/nateships/rolle && cd rolle
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -buildvcs=false \
  -ldflags "-s -w -X github.com/nateships/rolle/internal/version.Version=<version>" \
  -o rolle-rebuilt ./cmd/rolle
sha256sum rolle-rebuilt rolle   # rolle from the desktop package
```

The two hashes match. The Windows command carries an Authenticode signature, which changes its bytes: strip it first with `osslsigncode remove-signature -in rolle.exe -out rolle-unsigned.exe`, then compare. The desktop packages are signed, and on macOS notarized. They do not compare byte for byte. For those, the provenance attestation links to the source.

## Reset

`rolle reset` and **Settings → Advanced → Reset** remove the workspace, every keychain entry, the credential cache, and the AWS profiles rolle wrote.
