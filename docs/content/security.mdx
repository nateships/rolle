## Long-lived secrets stay in the keychain

Identity Center refresh tokens, Azure token caches, and IAM user access keys live in the OS keychain (macOS Keychain, Windows Credential Manager, Secret Service on Linux) under the service name `rolle`. Large tokens are split into chunks to fit platform limits.

## rolle caches short-lived credentials until they expire

A started session caches its temporary credentials in `credentials/` under the cache directory (see [Storage](/#storage)) with owner-only permissions. `credential_process` reads that cache. Each entry carries its expiry. The app renews or removes entries. An IAM user without MFA has no temporary credentials: its access key stays in the keychain and never enters the cache.

## rolle writes only its own AWS profiles

rolle marks each profile it writes with a `rolle_session` key. It refuses to touch a section that holds `aws_access_key_id` or other credential keys. rolle takes over a plain `[default]` section that only sets region or output, and restores it on stop.

## No telemetry

The app and the CLI collect nothing: no analytics, no crash reports, no usage data, no account. Every network connection rolle makes is one of these:

- The cloud providers you sign in to: Identity Center portals, AWS OIDC and STS endpoints, Microsoft Entra and Azure Resource Manager, Google APIs, and the consoles that **Open console** launches in your browser.
- `github.com`, for the update manifest at launch and every six hours while **Settings → General → Automatic updates** is on, for the update download you confirm, and for the issue form that **Report a problem** opens in your browser.

Nothing is sent that you did not ask for. The support bundle is a file in your Downloads folder; you decide whether to attach it to an issue.

You do not have to take that on trust:

- **Watch it yourself.** Run `rolle --debug` or set `ROLLE_DEBUG=1`. Every HTTP client in the process, the cloud SDKs included, goes through one transport that logs the method and host of each request, and nothing else. The desktop app's **Verbose logging** setting does the same, and the support bundle carries the last lines of that log.
- **Capability analysis in CI.** [Capslock](https://github.com/google/capslock) reads the Go call graph and reports which capabilities each package reaches through its whole dependency tree: network, process execution, file access, and so on. `capslock.json` in the repository is the recorded set, and the `capabilities` job fails a pull request that changes it. A dependency that starts talking to the network shows up as a diff in that file.
- **[OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/nateships/rolle).** An independent weekly rating of the repository's practices: pinned actions, branch protection, signed releases, token permissions, static analysis, and dependency updates.
- **Build provenance and reproducible builds** below tie each release file to the public source at a named commit.

## Enterprise networks

rolle verifies TLS against the OS trust store: the macOS Keychain, the Windows certificate store, or the Linux system bundle. A corporate root installed there, as TLS inspection products require, works with no rolle configuration. For a root that is not in the OS store, point **Settings → Advanced → Extra CA bundle** at a PEM file. **HTTPS proxy** routes every request through one proxy when the app cannot see your shell's `HTTPS_PROXY`. Both apply to the CLI and the app, including the AWS SDK calls.

## Signed updates

An Ed25519 key signs every release manifest. The desktop app verifies the signature before it installs an update. A Developer ID certificate signs the macOS builds, and Apple notarizes them. The release checksum file lists every asset, CLI archives and desktop packages alike, and carries a keyless Sigstore signature from the release workflow; [Install](/install#cli-archives) shows how to verify it.

## Build provenance

The release workflow writes a [SLSA build provenance](https://slsa.dev/provenance) attestation for every file in `checksums.txt`. It records the repository, the commit, and the workflow run that produced the file, and GitHub signs it with the workflow's identity. Verify a download with the GitHub CLI:

```sh
gh attestation verify rolle.dmg --repo nateships/rolle
```

A passing check means the file came out of `.github/workflows/release.yml` in this repository at the commit it names, not from a laptop or a fork.

## Reproducible builds

From 0.1.4 on, the CLI archives are built with `-trimpath` and no cgo, so the same source, toolchain, and flags give a byte-identical binary. To check a release, clone the tag with a clean tree, use the Go version that `go version -m rolle` prints for the released binary, and build:

```sh
git clone --branch v<version> https://github.com/nateships/rolle && cd rolle
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \
  -ldflags "-s -w -X github.com/nateships/rolle/internal/version.Version=<version>" \
  -o rolle-rebuilt ./cmd/rolle
sha256sum rolle-rebuilt rolle   # rolle from the release archive
```

The two hashes match. The desktop packages are signed and, on macOS, notarized, so they cannot be compared byte for byte; for those, the build provenance above is the link to the source.

## Reset

`rolle reset` and **Settings → Advanced → Reset** remove the workspace, every keychain entry, the credential cache, and the AWS profiles rolle wrote.
